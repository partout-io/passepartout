# Programming conventions

Follow the general and applicable language-specific programming conventions in
[Partout's AGENTS.md](partout/AGENTS.md) when working on Passepartout.
Read that file before making code changes; it is the shared source of truth for
these conventions. Rules concerning Partout's internal module layout remain
scoped to Partout.

Apply these rules to new or changed code. Existing deviations do not authorize
unrelated refactoring; keep changes within the task's scope.

## Text files

- Use UTF-8 and LF line endings on every platform, including Windows. Never
  introduce CRLF or stray carriage returns (`^M`) into source, configuration,
  scripts, generated text, or documentation.
- Preserve LF when writing files with PowerShell or generators. Check changed
  text files for carriage returns before finishing; normalize only files within
  the task's scope. Follow `.gitattributes` and `.editorconfig`.

## Strings

- Reuse existing shared strings before introducing new labels. Keep wording and
  meanings consistent across platforms. Do not create feature-specific string
  collections or duplicate existing labels under new keys.
- Localize user-facing prose, actions, accessibility labels, and error messages.
  Reuse the standard error presentation rather than introducing generic per-feature
  failure strings. Use locale-aware formatting for quantities and durations.
- Keep protocol names, identifiers, and other deliberately unlocalized vocabulary
  in the existing unlocalized definitions. Use those definitions directly; do not
  copy them into localized catalogs or generate duplicate resources from them.
  Raw configuration data and protocol syntax must not be translated.
- Localized source: use
  [Localizable.strings](app-apple/Sources/AppStrings/Resources/en.lproj/Localizable.strings)
  and the corresponding locale catalogs under
  `app-apple/Sources/AppStrings/Resources/*.lproj/Localizable.strings`. Add a key only
  when no existing key expresses the intended meaning. Never add protocol constants
  already defined in the unlocalized vocabulary.
- Apple: localized accessors are generated in
  [SwiftGen+Strings.swift](app-apple/Sources/AppStrings/SwiftGen+Strings.swift).
  Unlocalized definitions are in
  [Strings+Unlocalized.swift](app-apple/Sources/AppLibrary/L10n/Strings+Unlocalized.swift).
  Use the existing translation/SwiftGen workflow; do not edit generated accessors.
- Android: localized resources are generated in
  [localizable.xml](app-android/app/src/main/res/values/localizable.xml) and
  `app-android/app/src/main/res/values-*/localizable.xml` by
  [import-apple-strings.sh](app-android/scripts/import-apple-strings.sh).
  Unlocalized definitions already exist in
  [Strings+Unlocalized.kt](app-android/app/src/main/kotlin/com/algoritmico/passepartout/ui/Strings+Unlocalized.kt);
  use `Strings.Unlocalized` directly. Do not parse Swift constants into Android XML
  or add separate feature string files. Do not edit generated XML manually.
- Windows/Linux (`app-cross`): use `Localized(StringKey)` from
  [strings.h](app-cross/app/strings/strings.h) and
  [strings.cc](app-cross/app/strings/strings.cc). The catalogs and keys in
  [strings.inc](app-cross/app/strings/strings.inc) and
  [strings_keys.h](app-cross/app/strings/strings_keys.h) are generated by
  [import-apple-strings.ps1](app-cross/scripts/import-apple-strings.ps1); do not edit
  them manually. There is currently no dedicated unlocalized definitions file in
  app-cross. Do not treat that gap as a reason to add unlocalized vocabulary to the
  shared localized catalogs or invent per-feature string sets.

## Application architecture

- Use the same domain names and meanings across frontends. The shared application
  schema is `scripts/openapi.yaml`; update generated models through the generation
  workflow rather than editing them manually.
- Keep responsibilities separated: domain models define contracts; managers own
  business rules; repositories and strategies provide replaceable mechanisms;
  observables expose UI state and actions; context assembles dependencies; Theme
  supplies native presentation components; views render state and handle input.
- Views must use observables or injected presentation helpers, never managers,
  repositories, or tunnel implementations directly.
- `PassepartoutApp` is the root application composition on every platform.
  Its framework role may differ (for example, SwiftUI `App` or an Android
  composable). Supply its application dependencies through the context.
- Name components by responsibility (`Manager`, `Repository`, `Strategy`,
  `Observable`, `Context`). Preserve established names such as `VersionChecker`;
  do not introduce empty manager layers merely for naming symmetry.
- Assemble dependencies in `AppContext` or explicit factories. Share relevant
  state across application surfaces and support fake dependencies for tests and
  previews, including tunnel control through `TunnelObservable`.
- Distinguish observed state, pending actions, and failures. Make initial state
  available to subscribers, prevent stale asynchronous results from superseding
  newer actions, and give subscriptions and cross-domain effects clear owners.
- Keep platform integration behind explicit boundaries. Adapt navigation to the
  form factor while keeping business rules independent of the UI toolkit.
- Build Theme from stock native controls, supporting dynamic palettes,
  accessibility, and localization. Keep business logic out of Theme.
- Keep Partout external to the application logic. Delegate VPN implementation
  and VPN configuration import/export to it rather than duplicating that logic
  in Passepartout.
- Test application state transitions independently of the UI with replaceable
  dependencies. Verify native integration on the affected platform when a change
  affects that integration.

Keep platform implementation plans separate from these shared conventions.
